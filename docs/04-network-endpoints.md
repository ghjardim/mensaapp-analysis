# 04 — Network Map & API Endpoints

**Method:** static only. Hosts and endpoints come from the Dart AOT snapshot (`libapp.so`),
recovered with blutter (`_work/blutter/asm/…`, git-ignored, rebuild per the README). **No request
was sent to any Mensa server or Firebase project.** Raw extraction:
[`_evidence/api-calls.md`](_evidence/api-calls.md) (generated by `scripts/10-extract-api-calls.py`).
Working notes, including two analysis steps that were stopped and not retried, are in
[`_notes/investigation-log.md`](_notes/investigation-log.md).

| Firebase / Google endpoints | Google | Auth, Firestore, Storage, FCM, Analytics, App Check | SDKs (see 03). Hosts are inside the SDKs, not first-party literals |

The FlutterFlow-generated `ApiManager.makeApiCall` adds `https://` when a URL has no scheme.
There is **no certificate pinning**: no `badCertificateCallback`, `SecurityContext` or
`HttpOverrides` in `carteirinhas_mensa`. Traffic uses the default client and the system trust
store. Cleartext is blocked by the Android defaults (see 03).

## Authentication

The Bearer token is the **Firebase ID token** of the signed-in user (`auth/firebase_auth/auth_util.dart:187-274`:
`jwtTokenStream` → `FirebaseAuth.idTokenChanges` → `User.getIdToken`). Sign-in is via Firebase Auth
with Google, Apple or email (plugins in 03). `createEvent` and `createTags` also put a `"token"`
field inside the JSON body. Its source has not been traced yet.

## Endpoint inventory (api.mensan.org.br)

HTTP methods are **inferred** (see the log). FastAPI-style call names carry `__get`/`__post`/`__patch`/`__delete`
suffixes that map 1:1 to the enum objects passed to `makeApiCall`. The two remaining calls use a
fifth object, taken as PUT.

### Member profile (personal data)

| Method* | Path | Sends | Reads back |
|---|---|---|---|
| GET | `/get_member/` | — | `member.name`, `member.cpf`, `member.birth_date`, `member.gender`, `member.profession`, `addresses`, `emails`, `phones`, `legal_representatives` |
| GET / POST | `/missing_fields` | POST: `cpf`, `birth_date` | — |
| POST / DELETE | `/address/`, `/address/{id}/` | `state`, `city`, `country`, `address`, `neighborhood`, `zip`, **`latlong`** | — |
| POST / PUT / DELETE | `/email/`, `/email/{id}/` | `email_type`, `email_address` | — |
| POST / DELETE | `/phone/`, `/phone/{id}/` | `phone` | — |
| POST / DELETE | `/legal_representative/`, `…/{id}/` | `cpf`, `full_name`, `email`, `phone`, `alternative_phone`, `observations` | — |
| PATCH | `/pronouns` | `pronouns` | — |
| PUT | `/update_fb_profession/` | `facebook`, `profession` | — |

### Groups & authorizations
`GET /iam/groups/`, `GET /iam/roles/`, `GET /get_authorization_status` (reads `authorized_numbers`,
`pending_authorization[].workers`), `GET /get_pending_requests`, `GET /get_failed_requests`,
`GET /get_participate_in`, `GET /get_can_participate`, `POST /request_join_group` (`group_id`).

### Events calendar
`GET /calendar/public/future`, `GET /calendar/tags/`. Admin: `POST|PATCH|DELETE /calendar/admin/`
(`title`, `description`, `start_time`, `end_time`, `location`, `event_url`; delete takes `event_id`),
`POST|PATCH|DELETE /calendar/admin/tags/` (`name`, `description`).

### Volunteer program
`GET /volunteer/points/`, `/volunteer/leaderboard/` and `/leaderboard/me/` (`start_date`,
`end_date`), `/volunteer/names`, `/volunteer/categories/`,
`/volunteer/activities/full/{approved,rejected,unevaluated}/`. `POST /volunteer/activity/logs/`
(`category_id`, `title`, `description`, `activity_date`, `volunteer_name`, `media_file`, multipart).
Admin: `/volunteer/admin/evaluate-with-category/`, `POST /volunteer/admin/evaluations/`
(`activity_id`, `status`, `observation`), category create/patch/delete.

\* inferred, see above.

## Observations

**Reassuring:**
- **One first-party API host**, plus links to Mensa's own sites. No ad, attribution or data-broker
  hosts among first-party literals.
- Every API call is authenticated with a short-lived Firebase ID token. There are no hard-coded API
  secrets in the endpoint code.
- Fields are what a membership registry plausibly needs.

**Worth noting (capability present, not behavior proven):**
- **High-value personal data** goes through this API: **CPF**, birth date, gender, home address
  with **coordinates (`latlong`)**, phones, emails, Facebook profile, profession, and **CPF and
  contacts of a legal representative** (relevant for minor members, LGPD Art. 14). This is
  expected for the service. It raises the stakes on server-side access control, which **cannot
  be assessed statically and was not tested**.
- `latlong` on addresses: the app bundles `google_maps_webservice` and `flutter_google_places`
  (see `_work/blutter/asm/`), so address autocomplete plausibly sends typed addresses to Google
  Places and gets coordinates back. Not yet traced. Pending in 05.
- Admin endpoints (calendar, volunteer evaluations, categories) ship in every member's app.
  That is normal for FlutterFlow. Authorization must be enforced server-side. Their presence is not
  a vulnerability, and it was not tested.
- No certificate pinning. That is common and not a defect, but it means a device with a
  user-installed CA plus a debuggable/repackaged build could observe traffic. It also means a
  dynamic analysis on a test device would be straightforward.
